# Capture notifications, extra Ack, and gray-pick coordinates

[中文](capture-notifications-analysis.md)

On 2026-11-15 the user reported that v0.3.1 maintains a stable Bluetooth session with Valeo and can change ISO/gray-balance shooting settings. Automatic follow after each exposure produces `^<Error error_code="0x01" />`, while the session remains READY and manual download reads the latest image. This audit statically examines the retained DP-67 client, both WiView clients, classic 4.701 and shared 5.041 firmware. It executes no vendor code or hardware operations. The user report is not a device test performed by this static audit.

The strongest compatibility candidate is an **extra bare Ack after the new-image notification**, rather than interpreting `0x01` as busy. The traced vendor PictureTaken/ImageChange paths establish no requirement to send that notification Ack, and the firmware has an explicit no-current-command-handler branch constructing the same error. If an extra Ack's Error is accepted by a pending GetImage, it can explain an automatic-download failure with subsequent manual success. Logs and device testing are still needed to establish that causal sequence.

## PictureTaken / ImageChange paths and Ack

DP-67's receiver, `0x24a44..0x25128`, reads `busy` in the PictureTaken branch, selects an event and posts a processing message. Its application handler, `0x17360..0x17c6c`, consumes the complete `file_name`, splits on `/`, requires a first component of `.`, and resolves or creates the cached file object. `CDOSFile::Cache` (`0x30e70..0x3114c`) passes the object's full name as the sole file property to the same `CProtocolLayer::GetImage` (`0x26f00..0x27340`) used for ordinary downloads. This audit establishes no auto-only basename substitution or complete fixed-delay-before-download policy.

WiView 1.0.3's receiver, `0x29fd0..0x2a8a8`, calls `0x28718` for PictureTaken and `0x29a94` for ImageChange. Their common follow-up, `0x28664..0x28718`, **reads and discards the indicated attachment bytes; it does not send Ack**. No notification-Ack constructor is established in either traced chain. The corresponding 1.0.2 routes/parsers are retained separately.

Ack is context-specific:

| Context | Vendor evidence | Implementation implication |
| --- | --- | --- |
| PictureTaken / ImageChange notification | No bare-Ack requirement established in this audit | Do not acknowledge every received notification indiscriminately |
| Stop notification | WiView 1.0.3 `0x29c28..0x29ccc`: loads `^<Ack/>` at `0x29c40`, writes the link at `0x29c7c`; 1.0.2 `0x29504..0x295a8` | Preserve the explicit dedicated response |
| Image data / packet checking | DP-67 `0x257c0..0x264dc`; WiView 1.0.3 `0x31dc8`, `0x31e8c` contain Ack/Nak paths | A separate mechanism; the app still does not implement packet acknowledgements, and these paths do not justify ordinary notification Ack |

## Firmware path for `error_code="0x01"`

Classic 4.701's registered-name lookup, `0xe727c..0xe7320`, traverses the 9 registered PDA command types; Ack is absent. The incoming handler at `0xe6c5c` parses the command name and calls that lookup at `0xe6cec`. With no current handler pointer, `0xe6cfc..0xe6d28` calls OutgoingMessage creation at `0xe7b60` with message enum **12**. Creation reaches selector `0xe3c18` at `0xe7bd8`; enum 12 in jump table `0x3e002c` selects `0xe3e50`, whose `0xe3e50..0xe3e80` branch explicitly constructs **Error + error_code + 0x01**.

Shared 5.041 has an independently checked parallel path: incoming handler `0x102ddc` → lookup `0x1033fc`; null-handler branch `0x102e7c..0x102ea8` calls `0x103ce0` with enum 12; `0x103d58` reaches selector `0xfff64`, and the corresponding entry in table `0x46df20` reaches `0x10019c..0x1001cc`, constructing the same Error. This is a shared-dialect comparison, not proof of the user's Valeo firmware version.

Other constructors exist, so **the number alone does not identify a unique cause**. Classic generic constructor `0xb0b74` maps enum 2 to `0x01` and enum 3 to `0x02`. GetImage's own file-lookup failure at `0x912c0..0x912c8` passes enum 3, as does 5.041's corresponding `0x98504..0x9850c` branch. Classic image-processing / zero-buffer failures use separate constructor `0xb0ca4` and an `error` attribute such as `1ffc` / `8002`. These findings do not translate this report's `0x01` into file-not-saved or camera-busy.

The evidenced corrective direction is to remove unsupported notification Ack, testing notification handling separately from image packet acknowledgements. If the failure remains, preserve the actual request, raw Error and subsequent GetImage/Ack/Sync timing for further investigation. This audit does not justify treating every `0x01` as retryable busy.

## Save state and overlapping downloads

WiView 1.0.3's PictureTaken parser explicitly reads `busy`, `parametersReady`, `imageSaved` and the complete `file_name`. Explicit `busy=yes` creates a separate busy notification; it is not inferred from an error code. Both readiness flags default to false. Notification processing at `0x171b4..0x171fc` records image states 0/1/2, with imageSaved taking precedence; state accessors are at `0x4809c` and `0x48b88`. The extra `0x25570` call in the saved branch performs two-word bookkeeping arithmetic; it must not be mislabeled as download-queue submission. The UI branches on these states.

The cache-download function `GetBitmapBase` (`0x51234..0x516fc`) resolves local cache / request variants, then constructs GetImage at `0x5143c`. This traced construction path contains no image-state-equals-2 requirement. All UI scheduling was not reconstructed, so the audit does not claim the original always waits for imageSaved before any preview, or establish a universal mandatory parametersReady gate. DP-67 does not establish the same field requirement; absence of newer flags must not mean an older back is permanently unready. ImageChange has a separate refresh route and does not justify unconditionally starting an overlapping binary download.

## Gray-pick coordinate domain

WiView 1.0.3's extended GetImage constructor uses the exact format **`light="%d,%d"`** at `0x36240`, with a comma rather than a space. It asks the back to compute a gray sample. A UI instruction to pick white material does not mean the client computes Kelvin or guarantees suitable exposure.

The traced mapping is:

1. Sync's `picturedimensions` contains two comma-separated integers. At `0x2feb4..0x2ff64`, the larger value becomes grid width W and the smaller height H. The Sync target is global-object `+8`, so parser offsets `+0x104/+0x108` correspond to global `+0x10c/+0x110`.
2. Getters `0x38f10/0x38f28` return W−1/H−1. Full-preview initialization adds 1 at `0x78a90..0x78ab4`, making the initial ROI `[0,W)×[0,H)`.
3. `OnImageClick` (`0x765dc..0x768fc`) scales tap coordinates by the current ROI width/height divided by the displayed image rectangle dimensions, then adds the ROI origin. That image-grid point reaches the gray handler at `0x76860`; phone screen pixels are not sent directly.
4. Photo orientation parsing maps Portrait CCW = 0, Portrait CW = 1, Landscape = 2, Auto = 3. Gray handler `0x777f0..0x77bc0` leaves Landscape as `(x,y)`, maps CW to `(H−y,x)` and CCW to `(y,W−x)`. The traced subtraction contains no explicit `−1`. A different pixel-edge convention must not be described as the vendor's behavior.

The portrait display path was then traced further. At `0x5522c`, the actual photo orientation is read and passed with the decoded bitmap to wrapper `0x54d98..0x54f3c` at `0x5523c`. The wrapper reads bitmap width/height: Landscape = 2 expects width at least height; Portrait CCW/CW expects height at least width. Opposite dimensions produce explicit mismatch logs. A normal portrait bitmap is temporarily turned into landscape at `0x54ee8..0x54f18`: CW = 1 passes 270°, CCW = 0 passes 90° to `0x955a4`, then swaps width/height. This is **additional display rotation by the old PDA**.

`0x955a4..0x95814` creates the rotated bitmap and calls pixel kernel `0x94de4`. DIB constructor `0x92cfc` writes a positive height at `0x92d1c`. With this 24-bit bottom-up DIB layout, the 90° branch at `0x94ee8..0x94f94` is visually clockwise, `(sourceHeight−1−sourceY,sourceX)`; the 270° branch at `0x950f4..0x951b0` is counterclockwise, `(sourceY,sourceWidth−1−sourceX)`. The gray-point handler restores this temporary display rotation.

An inference from this chain is that **an Android view of the unchanged downloaded JPEG must not repeat the PDA's display rotation or inverse transform**. With ordinary full FIT, explicit per-photo Landscape / Portrait CW / Portrait CCW, positive PictureDimensions, photo orientation bound to the current JPEG, matching JPEG direction/aspect, and no additional EXIF/display rotation or unknown crop, the normalized JPEG point maps directly to:

| Photo orientation | Camera sampling grid |
| --- | --- |
| Landscape | W × H |
| Portrait CW or Portrait CCW | H × W |

These are **the camera image-grid coordinates used by the original PDA**, not proven raw MOS sensor pixels. Multiplying normalized positions by grid dimensions, flooring and enforcing valid bounds is an explicit Android boundary choice. The pixel kernel uses `−1`, while the old gray-point transform subtracts from W/H; bit-identical rounding at every edge is not claimed. Letterboxing produces no request.

Auto, missing orientation, contradictory dimensions/JPEG direction, arbitrary zoom ROI, unknown crop and automatic EXIF rotation remain outside this limited bridge. Matching aspect is a consistency check, not proof that an otherwise unknown crop does not exist. Retain point hints or manual coordinates in these cases. Hardware sampling results were not tested by this analysis.
