## Capture notifications and Error 0x01

[Complete analysis](../capture-notifications-analysis.en.md) of original DP-67 / WiView and classic 4.701 / shared 5.041 firmware establishes:

- Ordinary PictureTaken / ImageChange and similar asynchronous paths do not automatically send `^<Ack />`; WiView explicitly confirms Stop.
- The examined firmware PDA directories do not register ordinary Ack. Unknown-command handling reaches enum 12 and returns Error `0x01`. **Code 0x01 must not be called busy.**
- Packet-data Ack / Nak is a separate mechanism, still disabled in this app; it does not prove ordinary notifications need acknowledgement.

The old extra Ack could provoke Error before it is consumed by pending GetImage. This can explain the reported behavior, **without a user wireless trace proving that exact ordering**. Static evidence is archived under [capture-notifications](../../reference/dp67/analysis/capture-notifications/).

Version 0.3.2 removes these extra acknowledgements from ordinary sessions and laboratory automatic handling, retaining only dedicated Stop confirmation. It adds no blind retry, parametersReady hard gate or new shooting writer. A complete Error refusal differs from timeout: refusal alone does not force-close an otherwise usable connection; timeout still closes and requires manual reconnect followed by state inspection. Automatic-preview recovery still awaits user retesting.

## Error codes and refusal diagnostics

`WireNumbers.errorCode` strictly parses decimal or `0x` / `0X` hexadecimal unsigned DWORDs. `0x00` is zero, `0x01` is one and `0xffffffff` is valid. Negative, empty, overflowing or unknown syntax stays unknown and must not count as success.

The refusal exception retains original request / reply for internal diagnosis. Its user-facing prefix lists only request tag and attribute names, without request values. Known sensitive reply fields are redacted, so PIN, annotation, copyright and XMP are not inserted directly into error text. This remains a protocol / I/O error; Error does not establish physical Bluetooth loss or justify blindly resending a write.

## Back actions on the photo page

The photo page adds **Back image tools** and **Photo actions**. Tools opens processed preview, gray balance, pixel picking and back histograms. Actions reuses back marks, back notes, copy / move and deletion. Phone stars / local notes remain separate; folder creation / deletion / rename remain on Back.

Deletion requires a second confirmation showing the actual device and full photo path. Only directory read-back proving deletion removes the source from the phone list and its cache; deleting the selected photo chooses a neighbor when available. Refusal or failed verification retains local records for inspection.

Move verifies source absence and target presence before removing source records / cache and reading the target. Copy retains the source, and neither overwrites an existing destination. Failure does not prove nothing happened on the back; inspect actual directories before continuing. Arbitrary individual MOS rename is not added, and internal copy / move is not original-file download. Physical storage effects still need testing.

## Tap a white / gray area

Explicitly enter gray-balance picking mode, then tap a desired neutral white / gray area in the main preview. Pinch and double-tap still zoom. Letterbox and out-of-image taps send nothing.

Automatic sampling requires explicit orientation in current-photo metadata, `Sync.PictureDimensions`, current-preview SHA binding and consistent aspect evidence:

| Condition | Back reference grid |
| --- | --- |
| Landscape | max×min reference dimensions |
| Portrait CW / Portrait CCW | min×max reference dimensions |
| Auto, unknown orientation, missing or conflicting data | No automatic sampling request; manual coordinates remain |

The actual JPEG is displayed directly, without the extra transformation used for temporary rotation in the old PDA viewer. Inverse mapping considers fit, zoom and pan. Grid coordinates are not claimed MOS / RAW sensor pixels or proof that every firmware's crop relationship has been physically measured.

The app requests a sampled preview and Light from the back; it does not invent Kelvin / tint from phone JPEG pixels. Separate confirmations apply returned Light to the current photo or future captures. No confirmation means no commit. Future-capture settings still preserve the complete configuration and verify Sync.

Every preview refresh clears old metadata and samples. Sampled point, Light, SHA, photo and current connection must match. Reconnect, another photo or same-name replacement cannot reuse an old point. Tap mapping, current-photo commits and actual color effects remain unverified; the user's working v0.3.1 shooting gray-balance report does not establish them.

## Verification and delivery

Verification covers notifications without extra Ack, Stop confirmation, numeric errors / redaction, manual reading after refusal, point mapping / freshness, photo actions and existing setting read-back. Actual checks, counts and builds follow this version's [verification-status.json](../../research/reports/verification-status.json), [apk-verification.json](../../research/reports/apk-verification.json) and linked reports, without reusing an older APK's passing totals. Synthetic peers, app unit tests and API 36 emulators cannot replace real Valeo Bluetooth captures.

Physical retesting should record exact device / firmware / system / compatibility mode and request logs. Match at least 20 new photos by name, content, order and automatic display. Separately test orientation, tap boundaries, refresh invalidation, current-photo / future-capture confirmation and disposable photos for storage actions. Only observed results update the support table.

This build passes **168 tests**: 25 Python, 87 protocol JVM, 15 app JVM and 41 API 36 instrumentation tests, including a synthetic 20-photo sequence checking automatic download, filenames and decoded content. Debug/release lint has no errors; signature and 16 KiB alignment checks pass. The separate [signed-release check](../../research/reports/release-ui-verification.json) confirms retained settings after a 0.3.1 update, the fresh 1024 MiB default and offline Chinese/English, style and short-landscape display. [Screenshots](../screenshots/README.md) identify their respective build and evidence source.

The signed release APK is `Leaf2Android-0.3.2.apk`, accompanied by source, reference resources and SHA-256. A debug APK can be generated using the build instructions. App ID: `com.leaf2android`; minimum Android 12 / API 31; compile / target API 36. Matching release signatures allow in-place updates; private keys remain outside the repository. See the [user guide](../quick-start.en.md) for build / installation.

The 1024 MiB default preview cache, one-time migration, styles, system-following Chinese / English and laboratory remain. Complete MOS, continuous live view and remote release of this mechanical-shutter setup remain unimplemented. Historical 0.3.1 and earlier release notes are not rewritten as current results. Automatically attached files in the former workspace are retained without publishing personal content.
